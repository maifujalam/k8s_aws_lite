Vault Secret Injector (Bank Vault)

Webpage: https://bank-vaults.dev/

Configure Readonly Access to vault-init container to read secrets from vault using vault-secrets-operator.
1. Login to vault using root token:
    a. export VAULT_ADDR=https://vault.maifuj.com
    b. vault login
2. Enable insecure kubernetes authentication method in vault for vault-init container to read secrets from vault.
    a. Enable kubernetes authentication: vault auth enable -path=kubernetes-insecure kubernetes
    b. Configure kubernetes authentication method: vault write auth/kubernetes-insecure/config \
    kubernetes_host="https://$KUBERNETES_PORT_443_TCP_ADDR:443"
    c. Verify the configuration: vault read auth/kubernetes-insecure/config

    Key                                  Value
    ---                                  -----
    disable_iss_validation               true  [ Its disable the ssl validation of issuer]
    disable_local_ca_jwt                 false
    issuer                               n/a
    kubernetes_ca_cert                   n/a
    kubernetes_host                      https://10.96.0.1:443
    pem_keys                             []
    token_reviewer_jwt_set               false
    use_annotations_as_alias_metadata    false
3. Create a read-only policy for vault-init container to read secrets from vault.
    a. Create a policy file: cd tmp && vi vault-init-readonly.hcl
    b. Add the following content to the file:
        path "secrets/*" {
          capabilities = ["read","list"]
        }
    c. Create the policy in vault: vault policy write vault-init-readonly vault-init-readonly.hcl

4. Create a role for vault-init container to use the read-only policy.
    a. Create the role in vault: vault write auth/kubernetes-insecure/role/vault-init-readonly \
    bound_service_account_names=default \
    bound_service_account_namespaces=* \
    policies=vault-init-readonly \
    ttl=24h

    As there are many applications with their own custom SA,its better to give access to all SA in all namespaces to read secrets from vault.
    vault write auth/kubernetes-insecure/role/vault-init-readonly \
    bound_service_account_names='*' \
    bound_service_account_namespaces='*' \
    policies=vault-init-readonly \
    ttl=24h

    b.check the role: vault read auth/kubernetes-insecure/role/vault-init-readonly

5. Update tge configmap to set the default annotations for vault-init container to read secrets from vault.
    a. Edit the configmap: kubectl edit configmap vault-secrets-operator-config -n vault-secrets-operator
    b. Add the following annotations to the configmap:
        data:
          defaultAnnotations: |
            vault.security.banzaicloud.io/vault-addr: https://vault.maifuj.com
            vault.security.banzaicloud.io/vault-path: kubernetes-insecure
            vault.security.banzaicloud.io/vault-role: vault-init-readonly
            vault.security.banzaicloud.io/vault-skip-verify: "true"

    c. Create token for default sa: k -n default create token default
    d. Check the token: vault write auth/kubernetes-insecure/login role=vault-init-readonly jwt=<token_above>

6. Add annotations to the pod spec of the application to read secrets from vault.
    a. Edit the deployment: kubectl edit deployment <deployment_name> -n <namespace>
    b. Add the following annotations to the pod spec.Not the deployment/sts/replicaset.
        metadata:
          annotations:
            vault.security.banzaicloud.io/vault-addr: https://vault.maifuj.com
            vault.security.banzaicloud.io/vault-path: kubernetes-insecure
            vault.security.banzaicloud.io/vault-role: vault-init-readonly
            vault.security.banzaicloud.io/vault-skip-verify: "true"

     c. Validate by exec into the pod and check the secrets are injected into the pod.
        kubectl exec -it <pod_name> -n <namespace> -- /bin/sh
        cat /proc/1/environ | tr '\0' '\n' | grep -i my
        So,here tr is for translatingnull character '\0' to new line character '\n' and grep is for search.

        Important Notes:-
        - If we exec into the pod,do env | grep -i <vault_secret_env> to check the secret is injected into the pod or not.
           So,it displays the vault path as plaseholder instead of secret.
        - This is a security feature of vault-secrets-operator to avoid :-
            1. Secret leakage in pod logs.
            2. Secret leakage in pod env.
            3. Secret storing in disk or etcd.Which may leak.

     d. Note: If you are using vault-secrets-operator v0.1.0 or above, you can use the following annotations to inject secrets into the pod.
        vault.security.banzaicloud.io/vault-addr: https://vault.maifuj.com
        vault.security.banzaicloud.io/vault-path: kubernetes-insecure
        vault.security.banzaicloud.io/vault-role: vault-init-readonly
        vault.security.banzaicloud.io/vault-secret: secrets
        vault.security.banzaicloud.io/vault-secret-key: mykey
        vault.security.banzaicloud.io/vault-secret-env: MY_SECRET_ENV

 7. Disable vault-init to inject vault secret to pid-1?
    vault.security.banzaicloud.io/mutate: "skip"

 8. If the application runs pid other than 1 will vault secret still be injected there?
    Yes, the vault secret will still be injected into the pod, but it will not be available to the application running in a different PID namespace.
    The vault-init container injects the secrets into the environment of the main application container (PID 1), so if your application runs in a different PID namespace, it will not have access to those secrets.
